# 001: 릴리스 이동 태그 - 작업 목록

워크플로 문법은 작업마다 actionlint Docker 이미지로 검사합니다. Docker를 사용할 수 없으면 검증 저장소에서 GitHub이 워크플로를 오류 없이 불러오는지로 대신 확인합니다.

검증 저장소는 이 브랜치의 커밋을 고정 ref로 호출합니다. 따라서 검증 저장소에서 확인하는 작업은 이 브랜치를 push한 뒤에 진행하며, push할 때마다 사용자의 승인을 받습니다.

AC 시나리오는 각각 검증 저장소의 Release와 태그를 모두 지운 상태에서 시작합니다. 전제 조건이 필요한 시나리오는 검증 방법에 적힌 Release를 먼저 발행합니다. 초기화는 GitHub 쓰기이므로 사용자의 승인을 받습니다.

- [ ] T-1 (D-1): 진입점과 이벤트 검증 job
  - 대상 파일: `.github/workflows/move-tags.yml`
  - 내용:
    - `workflow_call` 진입점을 만들고, 입력 `app-client-id`와 시크릿 `app-private-key`를 필수가 아닌 항목으로 선언합니다.
    - 검증 job을 둡니다. 이 job은 권한을 비우고, 이벤트 이름과 작업 유형, 사전 릴리스 여부, 태그 형식을 확인합니다. `release.published`가 아니면 warning annotation을 남기고 정상 종료합니다. 사전 릴리스이거나 태그가 `vX.Y.Z` 형식이 아니면 갱신을 건너뛰도록 출력값을 설정합니다. 갱신 대상이면 major와 minor 값을 출력합니다.
    - 준비: 사용자가 검증 저장소와 전용 GitHub App을 만들고, App을 검증 저장소에 설치합니다. 검증 저장소에는 `workflow_dispatch`와 `release: types: [published]`에서 이 워크플로를 호출하는 호출 워크플로를 둡니다.
  - 완료 조건: 잘못된 이벤트와 갱신 제외 대상에서는 갱신 job이 실행될 조건이 만들어지지 않고, 갱신 대상에서만 major와 minor 값이 출력됩니다.
  - 검증 방법:
    - actionlint로 문법을 검사합니다.
    - 검증 저장소에서 `workflow_dispatch`로 호출하여 warning annotation, 정상 종료, 태그 목록 불변을 확인합니다 (moving-tags AC-14).
    - `v1.4.0-rc.1`, 사전 릴리스로 표시한 `v1.4.0`, `v1.4`, `v1`을 각각 Release로 발행하여 검증 job이 갱신을 건너뛰도록 판정하는지 확인합니다. 이동 태그가 있어야 하는 최종 검수는 T-3에서 수행합니다 (moving-tags AC-4).
  - 선행 작업: 없음

- [ ] T-2 (D-2): App 인증과 갱신 job
  - 대상 파일: `.github/workflows/move-tags.yml`
  - 내용:
    - 갱신 대상일 때만 실행되는 갱신 job을 추가합니다. 기본 `GITHUB_TOKEN` 권한은 비웁니다.
    - App 자격 증명 중 하나라도 없으면 실패를 보고하고 종료합니다.
    - GitHub 공식 App 토큰 액션으로 호출 저장소 한 곳에 한정하고 `Contents: write` 권한만 가진 설치 토큰을 발급합니다.
  - 완료 조건: 자격 증명이 있으면 토큰이 발급되고, 없으면 실행이 실패로 표시되며 태그가 바뀌지 않습니다.
  - 검증 방법:
    - actionlint로 문법을 검사합니다.
    - 자격 증명을 전달하지 않는 호출 워크플로로 Release를 발행하여 실행 실패와 태그 목록 불변을 확인합니다 (moving-tags AC-16).
    - 같은 버전으로 태그 푸시, Release 초안 저장, Release 발행을 차례로 수행하여 발행 시점에만 갱신 job이 실행되는지 확인합니다 (moving-tags AC-10).
  - 선행 작업: T-1

- [ ] T-3 (D-3): Release 조회와 이동 태그 쓰기
  - 대상 파일: `.github/workflows/move-tags.yml`
  - 내용:
    - `actions/github-script` step에서 Release 목록을 모든 페이지에 걸쳐 조회하고, 발행된 안정 Release 가운데 이벤트의 major 범위와 minor 범위에서 각각 최고 버전을 선택합니다.
    - 선택한 고정 태그를 커밋까지 해석합니다. 주석 태그는 태그 객체를 따라가서 커밋을 얻습니다.
    - 이동 태그 `vX.Y`와 `vX`를 조회하여, 대상과 같으면 쓰기를 생략하고, 없으면 생성하고, 다르면 갱신합니다.
  - 완료 조건: 정상 경로에서 두 이동 태그가 각 범위의 최고 발행 버전을 가리키고, 호출 저장소에만 태그가 생깁니다.
  - 검증 방법:
    - actionlint로 문법을 검사합니다.
    - 검증 저장소에서 경량 태그와 주석 태그로 각각 첫 Release를 발행하여 두 이동 태그의 커밋을 비교합니다 (moving-tags AC-1).
    - `v1.9.0`, `v1.10.0`을 차례로 발행하여 `v1`과 `v1.9`를 확인합니다 (moving-tags AC-2).
    - `v1.2.0`, `v1.3.0`을 차례로 발행한 뒤 `v1.2.1`을 발행하여 `v1.2`만 새 커밋을 가리키는지 확인하고, `v1.2.0` 실행을 재실행하여 두 이동 태그가 뒤로 이동하지 않는지 확인합니다 (moving-tags AC-3).
    - `v1.3.0`을 발행하여 `v1`과 `v1.3`을 만든 뒤, T-1의 제외 대상을 각각 발행하여 갱신 job이 실행되지 않고 `v1`과 `v1.3`의 참조가 바뀌지 않는지 확인합니다 (moving-tags AC-4).
    - 같은 Release 실행을 두 번 수행하고 실행 전후의 고정 태그와 이동 태그 참조를 비교합니다 (moving-tags AC-6).
    - 실행 후 이 저장소(`brighteast99/common-ci`)에 이동 태그가 생기지 않았는지 확인합니다 (moving-tags AC-11).
    - 더 높은 버전의 태그를 Release 없이 둔 상태에서 낮은 버전을 발행하고, 이어서 높은 버전을 발행하여 각 시점의 참조를 비교합니다 (moving-tags AC-12).
  - 선행 작업: T-2

- [ ] T-4 (D-3): 조회·갱신 오류 처리와 부분 실패 보고
  - 대상 파일: `.github/workflows/move-tags.yml`
  - 내용:
    - 이동 태그 조회에서 404만 태그 부재로 처리하고, 그 밖의 오류는 실패로 처리합니다.
    - 두 이동 태그를 각각 처리하고, 실패한 태그 이름과 작업(조회, 생성, 갱신)을 error annotation으로 남깁니다. 실패가 하나라도 있으면 마지막에 실행을 실패로 표시합니다.
  - 완료 조건: 갱신이 거부되면 실행이 실패로 표시되고 생성 요청을 보내지 않으며, 성공한 다른 태그의 갱신은 유지됩니다.
  - 검증 방법:
    - actionlint로 문법을 검사합니다.
    - `v1.2.0`을 발행하여 `v1`과 `v1.2`를 만든 뒤, `refs/tags/v1`의 `update`만 막는 시험용 tag ruleset을 App 예외 없이 적용합니다.
    - `v1.2.1`을 발행하여 실행 실패와 로그에 `v1` 생성 요청이 없는지 확인합니다 (moving-tags AC-5). `v1.2`가 새 참조를 유지하는지도 확인합니다.
    - ruleset을 지우고 같은 실행을 재실행하여 두 태그가 `v1.2.1`의 커밋을 가리키는지 확인합니다 (moving-tags AC-13).
    - 검수가 끝나면 시험용 ruleset이 남아 있지 않은지 확인합니다.
  - 선행 작업: T-3

- [ ] T-5 (D-4): 동시 실행 제어
  - 대상 파일: `.github/workflows/move-tags.yml`
  - 내용: 갱신 job에 호출 저장소 단위의 concurrency 그룹을 지정하고, `queue: max`로 대기 실행을 유지하며, 진행 중인 실행을 취소하지 않습니다.
  - 완료 조건: 같은 저장소의 갱신 job이 하나씩 실행되고, 대기 중인 실행이 취소되지 않습니다.
  - 검증 방법:
    - actionlint로 문법을 검사합니다. actionlint가 `queue` 키를 인식하지 못하면, 검증 저장소에서 GitHub이 워크플로를 불러오는지로 판단합니다.
    - `v1.2.1`, `v1.2.2`, `v1.3.0`을 짧은 간격으로 발행하여 실행이 겹치게 하고, 최종적으로 `v1.2`가 `v1.2.2`를, `v1.3`과 `v1`이 `v1.3.0`을 가리키는지 확인합니다. 발행 순서를 바꿔 한 번 더 확인합니다 (moving-tags AC-15).
  - 선행 작업: T-4

- [ ] T-6 (D-1): 이 저장소의 릴리스 워크플로
  - 대상 파일: `.github/workflows/release.yml`
  - 내용: `release: types: [published]`에서 `./.github/workflows/move-tags.yml`을 로컬 경로로 호출하고, App 자격 증명을 전달합니다.
  - 완료 조건: 이 저장소에 이동 태그가 없는 상태에서도 첫 Release 발행 시 호출할 수 있는 구성입니다.
  - 검증 방법:
    - actionlint로 문법을 검사합니다.
    - 브랜치를 push한 뒤 이 저장소의 Actions 화면에 워크플로 파일 오류가 없는지 확인합니다. 실제 실행은 main에 반영한 뒤 첫 릴리스에서 확인합니다.
  - 선행 작업: T-5

- [ ] T-7 (D-1, D-2): 워크플로 매뉴얼과 카탈로그
  - 대상 파일: `.github/workflows/README.md`, `README.md`
  - 내용:
    - `.github/workflows/README.md`에 move-tags의 호출 예시, 입력과 시크릿, 필요한 App 권한과 준비 절차, 실패 시 재실행 방법을 작성합니다.
    - 권장 ruleset을 안내합니다. 이동 태그를 보호하려면 전용 App을 이동 태그 ruleset의 예외로 등록해야 하고, `main`과 `vX.Y.Z` 보호 ruleset에는 App을 예외로 두지 않도록 적습니다.
    - 루트 `README.md`의 Reusable workflows 카탈로그에 move-tags 행을 추가하고 매뉴얼로 링크합니다.
  - 완료 조건: 매뉴얼만 보고 소비자가 App을 준비하고 워크플로를 호출할 수 있으며, 매뉴얼에 요구사항이나 설계 결정이 들어 있지 않습니다.
  - 검증 방법:
    - 매뉴얼의 입력, 시크릿, 권한이 `move-tags.yml`의 선언과 일치하는지 대조합니다.
    - 매뉴얼의 호출 예시가 검증 저장소의 호출 워크플로와 같은 구성인지 대조합니다.
    - writing-rules 기준으로 문서를 검토하고, 카탈로그 링크가 실제 파일로 이어지는지 확인합니다.
  - 선행 작업: T-5
