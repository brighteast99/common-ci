# 001 릴리스 이동 태그

## 요약

안정 릴리스에 대응하는 major와 minor 이동 태그를 관리하는 기능을 추가합니다.

## 배경과 이유

저장소의 버전 정책은 두 이동 태그를 제공하지만, 현재 저장소에는 이를 갱신하는 기능이 없습니다. 선행 워크플로는 major 태그만 갱신합니다. 이전 minor의 패치를 나중에 발행하면 major 태그가 과거 버전으로 이동할 수 있습니다.

## 범위에서 제외하는 것

- 릴리스와 고정 태그 `vX.Y.Z`는 사용자가 직접 만듭니다.
- 저장소 보호 설정(ruleset)은 이 기능의 요구사항에 포함하지 않습니다.

## clarify

### C-1. 버전 후보의 기준

- 관점: 판정 기준
- 답: 발행된 안정 GitHub Release를 기준으로 버전을 비교합니다. 고정 태그는 해당 Release의 버전과 커밋을 식별하는 데 사용합니다.
- 반영: FR-4, AC-12, Q-3

### C-2. 이동 태그의 부분 실패

- 관점: 시나리오의 예외
- 답: 두 태그를 동시에 이동할 필요는 없습니다. 재실행으로 실패한 갱신을 복구할 수 있어야 합니다.
- 반영: FR-8, AC-13

### C-3. 호출 이벤트와 인증 범위

- 관점: 범위의 경계
- 답: Release 발행 외의 경로로 호출되면 warning annotation을 남기고 종료합니다. 외부 호출에서도 호출 저장소에 설치된 전용 App을 사용합니다.
- 반영: FR-6, FR-9, FR-10, AC-14

### C-4. 동시 발행의 결과

- 관점: 수용 기준
- 답: 실행 순서가 달라도 major 태그와 각 minor 태그는 각각의 범위에서 가장 높은 발행 버전을 가리킵니다.
- 반영: NFR-5, AC-15

## 의사결정

### Q-1. 실행 시점 [결정]

- 배경: 고정 태그 생성과 GitHub Release 발행이 서로 다른 시점에 일어날 수 있습니다.
- 선택지:
  - (a) GitHub Release 발행 시 실행합니다. 발행 전에는 이동 태그가 바뀌지 않습니다.
  - (b) 고정 태그 푸시 시 실행합니다. GitHub Release가 없어도 이동 태그를 갱신할 수 있습니다.
- 결정: (a). 선행 워크플로와 동일하게 GitHub Release가 발행되는 시점에 이동 태그를 갱신합니다.
- 결정 주체: Donghwan Kim

### Q-2. 인증 범위 [결정]

- 배경: 저장소 쓰기 권한과 별개로 이동 태그를 갱신할 주체를 제한해야 합니다. 이동 태그 갱신 권한은 고정 태그의 보호에 영향을 주지 않아야 합니다.
- 선택지:
  - (a) 대상 저장소에 설치한 전용 GitHub App의 토큰을 사용합니다. 이동 태그 생성 및 갱신 규칙에서만 해당 App을 예외로 지정합니다.
  - (b) 호출자가 보호 규칙에서 승인된 토큰을 제공합니다. 호출자가 인증 주체와 자격 증명의 수명 주기를 관리합니다.
- 결정: (a). 이동 태그를 갱신하는 주체를 전용 App으로 한정하고, 고정 태그와 `main`의 보호 규칙에는 App을 예외로 등록하지 않습니다.
- 결정 주체: Donghwan Kim

### Q-3. 버전 후보의 기준 [결정]

- 배경: 고정 태그를 푸시하고 Release를 발행하기까지 시간이 걸릴 수 있습니다.
- 선택지:
  - (a) 발행된 안정 GitHub Release만 후보로 포함합니다. 발행 전에는 해당 버전이 이동 태그에 반영되지 않습니다.
  - (b) 고정 태그가 있는 버전을 후보로 포함합니다. 발행 전이라도 해당 버전이 이동 태그에 반영될 수 있습니다.
- 결정: (a). 소비자에게 제공할 버전은 GitHub Release 발행으로 확정합니다.
- 결정 주체: Donghwan Kim
