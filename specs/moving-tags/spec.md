# 릴리스 이동 태그

## 목적

소비자가 major 또는 minor 이동 태그를 참조하면 해당 범위의 최신 안정 릴리스를 사용할 수 있도록 합니다.

## 범위

- 포함: 발행된 안정 릴리스에 맞춰 이동 태그 `vX.Y`와 `vX`를 생성하고 갱신합니다.
- 제외: 릴리스와 고정 태그 `vX.Y.Z`는 사용자가 직접 만듭니다. 저장소 보호 설정(ruleset)은 이 기능의 요구사항에 포함하지 않습니다.

## 사용자 시나리오

- 첫 안정 릴리스 이후 소비자가 고정 태그와 두 이동 태그로 같은 커밋을 선택할 수 있습니다.
- `v1.3.0`을 릴리스한 뒤 `v1.2.1`을 릴리스하면, `v1.2`는 `v1.2.1`의 커밋으로 이동합니다. `v1`은 더 높은 버전인 `v1.3.0`의 커밋을 계속 가리킵니다.
- 저장소 권한 문제로 갱신할 수 없으면 릴리스 담당자는 실패를 확인할 수 있습니다.

## 기능 요구사항

- **FR-1**: 안정 릴리스의 고정 태그가 가리키는 커밋을 이동 태그 갱신 대상으로 사용합니다.
- **FR-2**: `vX.Y`는 같은 major와 minor 범위에서 SemVer 기준으로 가장 높은 안정 릴리스의 커밋을 가리킵니다.
- **FR-3**: `vX`는 같은 major 범위에서 SemVer 기준으로 가장 높은 안정 릴리스의 커밋을 가리킵니다.
- **FR-4**: 버전 비교에는 `vX.Y.Z` 태그로 발행한 안정 GitHub Release만 포함합니다. Release를 발행하지 않은 태그, Release 초안, 사전 릴리스, `vX.Y.Z` 형식이 아닌 태그는 후보에서 제외합니다.
- **FR-5**: 태그 조회나 갱신이 권한 오류 등으로 실패하면 작업을 실패로 보고합니다. 이동 태그가 존재하지 않을 때 새 태그를 생성합니다.
- **FR-6**: 호출 저장소의 릴리스 워크플로는 GitHub Release 발행 이벤트(`release.published`)에서 이동 태그 워크플로를 호출합니다. 고정 태그 푸시와 Release 초안 저장은 호출을 시작하지 않습니다.
- **FR-7**: 호출 저장소의 릴리스 워크플로에서 job 단위로 호출할 수 있도록 reusable workflow를 제공합니다. 이동 태그는 호출 저장소에 생성하거나 갱신합니다.
- **FR-8**: 이동 태그 중 하나만 갱신된 상태에서 실행이 실패하면 성공한 갱신은 유지합니다. 같은 실행을 다시 실행하면 각 태그의 상태를 확인하고, 현재 발행된 안정 Release를 기준으로 갱신이 필요한 태그를 처리합니다.
- **FR-9**: Release 발행 이벤트 외의 경로에서 호출되면, GitHub Release 발행 시에만 사용할 수 있다는 warning annotation을 남기고 태그 변경 없이 종료합니다.
- **FR-10**: 호출자가 전달한 전용 GitHub App의 자격 증명으로 호출 저장소에 한정된 설치 토큰을 발급하고, 그 토큰으로 이동 태그를 씁니다.

## 비기능 요구사항

- **NFR-1**: 같은 안정 릴리스를 다시 처리해도 최종 태그 상태가 달라지지 않으며, 고정 태그는 그대로 유지됩니다.
- **NFR-5**: 같은 저장소에서 여러 안정 Release의 발행 또는 재실행이 겹쳐도, 처리가 끝나면 각 이동 태그는 해당 범위의 가장 높은 발행 버전을 가리켜야 합니다.

## 수용 기준

- **AC-1 (FR-1, FR-2, FR-3, FR-5)**: 이동 태그가 없는 저장소에서 `v1.2.3`을 처리하면 `v1.2`와 `v1`이 고정 태그가 가리키는 커밋을 가리킵니다. 고정 태그가 주석 태그인 경우에도 결과는 같습니다.
- **AC-2 (FR-2, FR-3)**: `v1.9.0` 다음에 `v1.10.0`을 처리하면 `v1`은 `v1.10.0`으로 이동하고, `v1.9`는 기존 값을 유지합니다.
- **AC-3 (FR-2, FR-3)**: `v1.3.0`과 `v1.2.0`이 릴리스된 상태에서 `v1.2.1`을 처리하면 `v1.2`만 새 커밋을 가리킵니다. 이어서 `v1.2.0`을 재처리해도 두 이동 태그는 뒤로 이동하지 않습니다.
- **AC-4 (FR-4)**: `v1`과 `v1.3`이 이동 태그로 있는 상태에서 `v1.4.0-rc.1`, 사전 릴리스로 표시된 `v1.4.0`, `v1.4`, `v1`을 각각 Release로 발행해도, 워크플로는 태그를 생성하거나 갱신하지 않고 기존 이동 태그의 참조 값도 바뀌지 않습니다.
- **AC-5 (FR-5)**: 기존 이동 태그의 갱신 요청이 권한 부족이나 저장소 규칙으로 거부되면, 작업은 실패를 보고하고 해당 태그를 새로 생성하려고 시도하지 않습니다.
- **AC-6 (NFR-1)**: 같은 안정 릴리스를 두 번 처리하면 첫 처리 직후와 두 번째 처리 직후의 태그 목록 및 참조 값이 같으며, 두 처리 모두 처음의 고정 태그 참조를 보존합니다.
- **AC-10 (FR-6)**: `v1.2.3` 태그를 푸시하고 해당 Release를 초안으로 저장해도 이동 태그 갱신이 시작되지 않습니다. Release를 발행하면 갱신 job이 실행됩니다.
- **AC-11 (FR-7)**: 다른 검증 저장소의 릴리스 워크플로가 reusable workflow를 job으로 호출하면, 이동 태그가 호출 저장소에만 생성되거나 갱신됩니다.
- **AC-12 (FR-2, FR-3, FR-4)**: `v1.3.0` 태그만 있고 해당 Release가 미발행인 상태에서 `v1.2.1`을 안정 Release로 발행하면 `v1`과 `v1.2`는 `v1.2.1`의 커밋을 가리킵니다. 이후 `v1.3.0`을 안정 Release로 발행하면 `v1`과 `v1.3`은 `v1.3.0`의 커밋을 가리킵니다.
- **AC-13 (FR-5, FR-8)**: `v1.2.1`을 처리하는 중 이동 태그 하나의 갱신은 성공하고 다른 하나는 실패하도록 하면, 실행은 실패를 보고하고 성공한 태그는 새 참조를 유지합니다. 실패 원인을 해소한 후 같은 실행을 다시 실행하면 두 태그가 모두 `v1.2.1`의 커밋을 가리킵니다.
- **AC-14 (FR-9)**: 수동 실행 이벤트로 reusable workflow를 호출하면 warning annotation이 표시되고, 실행이 실패로 표시되지 않으며, 이동 태그가 변경되지 않습니다.
- **AC-15 (FR-2, FR-3, NFR-5)**: `v1.2.1`, `v1.2.2`, `v1.3.0` 발행에 따른 실행이 겹치면, 처리가 끝난 뒤 `v1.2`는 `v1.2.2`를, `v1.3`과 `v1`은 `v1.3.0`을 가리킵니다. 실행 순서를 바꿔도 결과는 같습니다.
- **AC-16 (FR-10)**: App 자격 증명 없이 Release 발행 이벤트로 호출하면 실행이 실패를 보고하고, 이동 태그를 변경하지 않습니다.
